## 1. 背景と目的

要件定義書には「オーダー」「伝票」という現行運用由来の概念があったが、**「オーダー」＝ P0 で実装済みの出庫依頼（`stock_requests`）であることが確定した**（[20](./20_P1-E_決定事項.md) D-20260801-07）。「在庫が二重に動く」（オーダー用の在庫処理と出庫依頼の在庫処理が別々に存在する）リスクは発生しない。

ただし実物サンプル分析（本書 §6-1）から、紙の資材発注書は**1オーダー番号の下に商品が複数行並ぶ**のに対し、現行の出庫依頼は**現場1つ＋商品1つ＋数量1つの単票**であることが分かった。このため目的を次の3点とし、①を先行実装する（[20](./20_P1-E_決定事項.md) D-20260801-08、[21](./21_P1-E_実装計画.md)）。

1. **出庫依頼を複数商品まとめて・素早く依頼できる形に変更する**（`orders` によるグルーピング。実装済み）
2. 出庫依頼（オーダー）に**確定数量修正・明細追加・事務の承認**を行えるようにする（実装済み）
3. **資材発注書として印刷・保管**できるようにする（紙運用は残す。既存の紙様式を踏襲。自社/リース区分・半端もん判定・資材種別も表示する。実装済み）

## 2. 前提（P0 を壊さない）

| 項目 | 内容 | 根拠 |
|------|------|------|
| 出庫依頼ステータス | `requested → accepted → shipped / cancelled` | `docs/09` |

| 現場マスタ拡張要否 | 現場コード／元請名／元請コード／工事番号／資材種別を自動表示したい。**現状 `sites` に元請・工事番号・資材種別の列はない**（本書作成時点でコード確認済み） | `003_sites.sql` |
| 帳票のスナップショット | 帳票確定時点の現場名・コード・元請情報等を**保存**し、後からマスタを変更しても過去帳票は変わらない | 要件定義書 |

### 2-1. 設計原則

1. `stock_requests` を含む P0 テーブル・RPC は**拡張または新規テーブル追加**とし、既存フローを壊さない
2. ~~オーダー番号は外部（旧システム）由来の参照キーとして扱う~~ → **システムが自動採番する**（D-20260805-01 #8）。列は text のまま保持し、将来クライアントが接頭辞・桁数の規則を定めても型変更を伴わないようにする
3. 帳票はスナップショット方式（発行時点のデータをコピー保存）とし、マスタの `id` 参照のみに頼らない
4. 用語は `docs/10` に従う。「オーダー」「依頼」の同義性が確定するまでは、本書・関連ドキュメントで両方の語を併記する

## 5. データ設計の方向性（ゲート0前ドラフト・未確定）

> migration 詳細は **E-U-1〜E-U-3 確定後**に本節を具体化し、[21](./21_P1-E_実装計画.md) ゲート1の成果物とする。以下は要件定義書記載のテーブル名を仮置きした概念モデルにすぎない。

### 5-1. テーブル（仮称・未確定）

**実装済みの構造**（migration 055〜064）:

```text
orders（オーダー＝1回の依頼のまとまり。order_number は自動採番）
  └─ stock_requests（明細。既存テーブルに order_id を追加して所属を表す）
```

- 明細は既存の `stock_requests` をそのまま使う。専用の `order_items` は作らない
  （ステータス遷移・在庫連動を既存フローのまま維持するため。`docs/09` を壊さない）
- `orders` が持つのは番号・納期・ヤード積込日・承認記録のみ
- ~~`slips` / `slip_items`~~ は D-20260805-06 で廃止（`slips` テーブルは未使用のまま残置）

### 5-2. `sites` 拡張（不要と確定）

元請（D-20260801-02）・資材種別（D-20260801-10。オーダー内容から自動判定）とも `sites` への列追加は**不要**と確定した。

### 6-1. 実物サンプルの項目（`資材管理実装/S__33292291_0.jpg`, `S__33292292_0.jpg` より）

**帳票名**: 資材発注書（オーダー1件＝1〜複数ページ、ページ番号・オーダー番号は各ページ共通ヘッダーに繰り返し表示）

| 区分 | 項目 | 備考 |
|------|------|------|
| ヘッダー（オーダー単位） | ページ、オーダー番号 | オーダー番号は旧システム由来（例: `37187`）。桁数・採番規則は E-U-4 未定 |
| ヘッダー | 現場名 | 例: 「サンプル住宅9号棟」 |
| ヘッダー | 納期 | 例: 「7/4 朝一」。自由記述に近い |
| ヘッダー | 発注者名 | 例: 「サンプル組E①」。vendor（業者）名に相当すると推定。**元請ではない** |
| ヘッダー | ヤード積込日 | 例: 「07月03日(金) 宵積」 |
| ヘッダー | 運転手／リフトマン | サンプルでは空欄 |
| ヘッダー | 伝票備考 | サンプルでは空欄 |
| ヘッダー | 運送区分／運送情報 | サンプルでは空欄 |
| ヘッダー | 合計重量 | 明細から自動計算と推定（例: 「6,391.9 Kg」） |
| 明細（行単位） | 商品コード、名称、数量、ヤード名、商品備考 | ヤード名は出荷元センター名（例: 「サンプル市A」）。**資材種別ではない** |
| 手書き（印刷後の追記） | 伝票番号（例: `(伝) 34022`）、社内管理番号（例: `309-206`） | **システムには入力しない**。別システム由来で連携できず二重入力になるため（D-20260805-06） |

**確認できなかった項目**（要件定義書 `E-REQ-07`/`E-REQ-08` にあるが実物サンプルに無い）: 元請名、元請コード、工事番号、資材種別。次回ヒアリングで要件定義書側の要否を確認する（[20](./20_P1-E_決定事項.md) D-20260801-01, 02）。
