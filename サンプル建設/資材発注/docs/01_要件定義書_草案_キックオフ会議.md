# 仮設資材 在庫・発注・リース管理システム 要件定義書（草案）

**根拠資料**: 会議文字起こし（kickoff-meeting.pdf、TurboScribe）  
**作成日**: 2026-05-11  
**ステータス**: 草案（顧客確認・現行システム調査後に改訂）

---

## 1. 背景・目的

### 1.1 背景

- 現行の在庫・発注・リース周りのシステムは、**2028年前後（会議上は「あと2年半」等の言及あり）**を目処に利用継続が難しくなる見込みがある。
- リース品の一部は現行システムに載せきれておらず、**別Excelで補完管理**している。
- 業者向けログインアカウントが約**20**あり、業者の入替時にIDの付け替え等の運用が発生している。

### 1.2 目的

- 現行と同等以上に、**在庫管理・発注（オーダー）・入出庫・現場登録**を行えるシステムへ移行する。
- **リース**についても、可能な範囲で**一元可視化**し、Excel併用を減らす。
- 業者が**在庫の有無・残少**を把握でき、**事前連絡**や補充判断がしやすくする。
- 移行時は**動作検証を重視**し、現場業務を止めない品質で切り替える。

## 2. ステークホルダー・利用者

| 役割 | 想定 | 主な操作 |
|------|------|-----------|
| サンプル建設（社内） | 在庫・発注の管理者 | マスタ整備、在庫調整、発注判断、リース状況確認 |
| 二次業者（業者） | 現場から資材依頼 | 資材依頼（オーダー）、必要に応じて希望日・数量入力 |
| 開発側 | 構築・保守 | 要件確定、実装、マニュアル、移行支援 |

---

## 3. 現行システムから読み取れる業務（会議ベース）

### 3.1 大枠の機能ブロック

1. **在庫管理**（サンプル建設側が主体）
2. **オーダー登録**（業者がログインし、必要資材を入力）
3. **仕入・入買**（会議では「3分くらいまで」との言及 ※詳細は現行画面で要確認）
4. **現場登録**
5. **二次業者への出庫**（業者が入力した内容を基に、社内で発注・手配）

### 3.2 現行の運用フロー（要確認・図示推奨）

- 業者がシステムに入り**材料が欲しい**旨を入力 → サンプル建設側で**在庫の有無を確認** → なければ**発注**、あれば**そのまま送付**（会議発言ベース）。
- 在庫が足りず納期に間に合わない場合は、**電話等の個別連絡**、**LINE**、**リースの手配・返却予定の連絡**などが発生している。

### 3.3 リース（現状）

- システムに**一部のみ**入っている項目と、**入っていない項目**がある。
- **自社在庫がない材料で完リース**のものは**Excel**で管理。
- **自社在庫と混合**のものは現行システム側で管理している、という整理（会議内容）。

### 3.4 利用しているマスタ（会議で言及）

- **現場マスター**
- **得意先マスター**
- **現場商品**（現場と商品の紐づけと解釈）
- **ログイン担当マスター**（業者に渡すID。業者変更時にコード付け替え等）
- **管理マスター**

※「見積」は基本触っていない、との発言あり。単価は変動するが頻繁ではない、等。

## 4. 機能要件（優先度付き草案）

### 4.1 P0（初回リリースに含めたい）

| ID | 要件 | 詳細・受入条件のたたき台 |
|----|------|-------------------------|
| F-01 | 現場マスタ | 一覧・登録・編集・（論理）削除方針 |
| F-02 | 得意先マスタ | 同上 |
| F-03 | 商品マスタ | 追加・編集、コード有無の整理方針に対応 |
| F-04 | 現場×商品 | 現場ごとに扱う商品の紐づけ |
| F-05 | 在庫照会 | 社内・業者が**在庫数量を参照**できる（権限で差分可） |
| F-06 | 業者からの資材依頼（オーダー） | 現場・資材・数量・日付等の必須項目 |
| F-07 | 依頼の社内通知 | **システム内通知**を優先（会議合意） |
| F-08 | 入庫・出庫 | 在庫数の増減が矛盾なく反映される |
| F-09 | 認証 | 将来的にURL一元化＋利用者名入力等の方針に沿った設計（下記4.3） |
| F-10 | 監査・履歴 | いつ誰がどの在庫・依頼を変更したか追える（最低限） |

### 4.2 P1（初回後または同一フェーズに含める候補）

| ID | 要件 | メモ |
|----|------|------|
| F-11 | リースの一覧・貸出状況 | 「いまどれだけリースで貸し出しているか一瞬で」会議要望 |
| F-12 | Excelリースデータ取込 | 共有Excelを基にスキーマ定義・取込バッチ |
| F-13 | 残少アラート | 閾値・対象者の定義 |
| F-14 | LINE通知（管理者向け） | 約10名弱への通知。ダッシュボードと併用可 |
| F-15 | 希望納期・納期不可時のワークフロー | 「いつ届くか見たい」「間に合わないときの社内フロー」をシステム化 |

### 4.3 認証・ログイン方針（会議での方向性）

- **業者ごと固定IDを20配布**する方式から、**同一URL＋オーダー時に施工班名等を入力**して区別する方式への移行が**方向性として妥当**との認識（会議）。
- **同時オーダー**（現場終了後に集中）への耐性を要件に含める（同時20〜30規模を会議で言及）。

### 4.4 非機能要件（草案）

| 項目 | 内容 |
|------|------|
| 可用性 | 営業時間内の利用を想定。メンテ窓口の定義 |
| 性能 | ピーク時の同時オーダー（目標同時ユーザー数・応答時間は別紙で数値化） |
| セキュリティ | ロール分離、トークン・鍵の保管方針（コード直書き禁止） |
| バックアップ | 日次スナップショット等 |
| 品質 | 移行前の**検証環境**でのシナリオテスト必須 |

## 5. データ移行・クリーンアップ

会議で言及された内容を要件化：

- 現行の**在庫数量・商品名**等を移行する方針。
- **商品コードを使っていない・使わない商品**の整理、**削除**を移行時に実施したい。
- 急な本番切替による**大量エラー**を避けるため、**段階的検証**と**ロールバック手順**を用意する。

## 7. 依存・前提（顧客側）
