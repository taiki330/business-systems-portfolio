## 4. Phase 詳細

ゲート0完了（D-20260801-07, 08）を受けて、以下の順序で進める。**各Phaseの着手にはゲート1（テーブル設計確定）が必要**で、まだ通過していない。

### Phase E-1 — 出庫依頼画面の作り直し（先行課題）

要件は [20](./20_P1-E_決定事項.md) D-20260801-08, 09 で確定。

| | |
|---|---|
| **目的** | 現場（vendor）が複数商品をまとめて・素早く出庫依頼できるようにする |
| **依存** | ゲート0（完了）、ゲート1 |
| **要件①** | **現場入力の廃止**。ログイン中の現場アカウントに直接紐づく現場（`app_users.site_id`）を自動適用する |
| **要件②** | **予定数量ベースの一覧選択**。事務が立てた予定（`site_product_plans`）の商品を一覧表示し、数量を入力していく |
| **要件③** | **「その他」枠**として現行同様の検索選択も併設し、予定外の資材も依頼できる |
| **要件④** | 1回の操作で複数商品×数量をまとめて登録できる（オーダー番号相当でグルーピング） |
| **前提** | **1アカウント＝1現場**。`app_users.site_id` を追加してアカウントに現場を直接持たせる（D-20260801-14）。現場選択 UI は出さない |
| **未確定（ゲート1で確定）** | ・グルーピングの表現方法（`stock_requests` への列追加か新規テーブルか）<br>・`app_users.site_id` の NOT NULL 可否と、role=vendor のときのみ必須とする制約の実装方法<br>・オーダー番号列の型・NULL 許容（採番規則は後日埋めるため、当面 NULL 可が濃厚） |
| **DB** | ①`app_users.site_id` 追加 ②`stock_requests` 拡張または新規グルーピングテーブル。`site_product_plans` は実装済みのため流用 |
| **App** | ①`/requests/new` を全面的に再構成 ②`/users/new`・`/users/[id]/edit` に現場選択を追加（role=vendor のとき） |
| **完了条件** | ① vendor が現場を選ばずに依頼できる ② 予定数量の商品が一覧で並び、数量入力だけで複数まとめて登録できる ③ 予定外の商品も検索して追加できる ④ 既存の受付/出庫/キャンセル操作に無回帰 ⑤ P0 出庫依頼フロー（`docs/09`）を壊さない |
| **実装済み（2026-08-01）** | migration 054/055 適用・動作確認済み。その後 057 で `create_order_with_requests` RPC を追加し、**オーダーと明細の登録を1トランザクション化**（それ以前は App 側で orders → stock_requests を順に INSERT していたため、明細の失敗時に空のオーダー行が残る余地があった） |
| **実装済み（2026-08-06）** | migration 068。事務の発行フローを **1現場＝1アカウント** としてDB制約化。アカウントの業者紐付けを廃止し、表示名は現場名を既定、招待メールを既定とした（D-20260806-01） |
| **改善アイデア（未実装・優先度低）** | 予定数量の一覧が長くなると入力しづらいため、商品カテゴリ（`product_categories`。P7で実装済み）ごとにタブ分けして表示する案。実物サンプルの「ダーフィン」等の商品ラインもカテゴリ相当。ユーザー発言（2026-08-01）「ダーフィンタブとかカテゴリとかのタブ作って現場の依頼と同じように数入力するだけみたいな」 |

### Phase E-2 — 伝票番号・確定数量修正

| | |
|---|---|
| **目的** | ~~E-REQ-02〜05~~ → **E-REQ-02（確定数量修正）のみ**。E-REQ-03〜05（伝票番号）は D-20260805-06 で取り下げ |
| **依存** | Phase E-1 |
| **前提** | **1オーダー＝1回の出庫が基本**（D-20260801-11）。複数伝票は許容するが主動線にはしない |
| **実装済み（2026-08-01）** | migration 056（`slips` テーブル／`update_stock_request_quantity` RPC）。`/orders` 一覧・`/orders/[id]` 詳細で、出庫前の確定数量修正と伝票番号の追加・削除が可能 |
| **実装済み（2026-08-05）** | `E-REQ-01`／`E-REQ-02`: `/orders` に**オーダー番号での検索**と現場絞り込みを追加。番号は自動採番（059）で発注書に印字され、事務は紙の番号で該当オーダーを呼び出す（D-20260805-03 ④）<br>migration 062: **既存オーダーへの明細追加**（`add_order_item` RPC）。センターが紙に手書きした追加分を事務が登録する（D-20260805-03 ⑤(b)） |
| **実装済み（2026-08-05）** | **事務による承認**（migration 063、D-20260805-04）。承認は記録のみで出庫をブロックしないため、`stock_requests` のステータス機械（`docs/09`）は変更していない。`orders.approved_at` に独立して記録し、`/orders` 一覧に承認状態、詳細に承認・取消ボタン（admin のみ）を表示 |

### Phase E-3 — 資材発注書（帳票・PDF出力）

| | |
|---|---|
| **目的** | E-REQ-08〜10, 12, 13（帳票表示・PDF化・スナップショット保存・自社/リース区分・半端もん判定） |
| **依存** | Phase E-1, E-2 |
| **前提** | 帳票項目は [18](./18_P1-E_設計整理.md) §6-1（実物サンプル）を正とする。資材種別はオーダー内容からシステムが自動判定（D-20260801-10）。元請は表示しない |
| **未確定** | 資材種別の自動判定ロジック（`product_categories` の流用可否）はゲート1で設計 |
| **実装済み（2026-08-01）** | migration 058（`get_order_requester_label`）。`/orders/[id]/print` でA4・複数ページの印刷プレビュー（ブラウザの印刷機能でPDF化）。表示項目: オーダー番号・ページ・現場名・依頼日時・発注者名・伝票番号／明細（商品コード・名称・数量・区分・半端） |
| **実装済み（2026-08-05）** | 帳票の残項目を反映（D-20260805-01 / 02）: 納期・ヤード積込日・合計重量（商品重量から自動計算）・自社/リース区分（`product_ownership_kind` で自動判定）・ヤード名（サンプル市A固定）。運転手・リフトマン・運送区分・運送情報・伝票備考・商品備考は**手書き用の空欄**として枠のみ設置 |
| **実装済み（2026-08-05）** | `E-REQ-10` **スナップショット保存**（migration 066、D-20260805-10）。依頼登録時点の商品情報・自社/リース自動判定・現場名・発注者名を固定して保存し、後からマスタを変更しても帳票表示が変わらないようにした。過去分のオーダーは対象外（NULLのままマスタ参照にフォールバック） |

Phase 完了条件・UAT・依存関係マトリクスは、ゲート1でテーブル設計が固まった時点で [17](./17_P1-B_実装計画.md) の形式に合わせて具体化する。
