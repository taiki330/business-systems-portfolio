## 3. 認証方式（確定）

### 3-1. 採用方式

- **Supabase Auth（email + password）**
- 内部ユーザー・業者ユーザー共に同じ仕組みでログイン
- パスワードリセットは Supabase Auth 標準のメール機能を利用

### 3-2. ユーザー作成・管理

- 当初は **管理者が Supabase ダッシュボードから手動で発行**（招待メール）
- 業者 20 アカウント分の発行は本番切替時に一括対応
- セルフサインアップは MVP では**有効にしない**

### 3-3. 採用しなかった案

| 案 | 不採用理由 |
|----|------------|
| 同一 URL ＋施工班名入力（`docs/01` §4.3 方向性） | 認証なしで現場絞り込みするには別途トークン URL 等が必要。MVP 安定性を優先 |
| マジックリンク | メール受信環境が不安定な業者がいる可能性。パスワード方式の方が運用問い合わせを減らせる |
| OAuth（Google 等） | 業者側のアカウント環境を前提にできない |

## 4. 業者と現場の紐付け（確定）

### 4-1. 採用方式: 1 業者:多現場

- 業者は **複数の現場を担当できる**
- 業者と現場の紐付けは **多対多テーブル `vendor_sites`** で表現

### 4-2. 新規テーブル案

```text
vendors
  id           uuid PK
  name         text not null
  note         text
  created_at, updated_at

app_users
  id           uuid PK   -- auth.users(id) と 1:1
  role         text check in ('internal', 'vendor')
  display_name text
  vendor_id    uuid       -- role='vendor' のとき必須、internal は NULL
  created_at, updated_at

vendor_sites
  vendor_id    uuid not null
  site_id      uuid not null
  primary key (vendor_id, site_id)
```

- 既存 `sites` テーブルには変更を加えない（`vendor_id` を直接持たせない）
- 既存 `stock_requests.requested_by` は **text のまま user_id 文字列を入れる**（型変更は P2）

### 4-3. 業者から見える現場

```text
sites のうち
  exists ( select 1 from vendor_sites vs
           join app_users u on u.vendor_id = vs.vendor_id
           where u.id = auth.uid() and vs.site_id = sites.id )
```

→ RLS policy（後述 §7）で表現。

### 4-4. 業者から見える商品

- **全商品（マスタ参照は全許可）**。site_products との関係は「並び替え補助」（`docs/11` の方針を維持）
- 制限を強める仕様は MVP 外

### 4-5. 業者から見える出庫依頼

- `stock_requests` のうち **`requested_by = auth.uid()::text` のもののみ**
- 同じ業者の別ユーザーが作った依頼は見えない（最小権限）
- 必要なら将来 vendor 全体で共有可（P2）

## 5. 業者向け倉庫在庫画面（確定）

### 5-1. URL とアクセス

| URL | 内容 | アクセス可 |
|-----|------|-----------|
| `/stock` | 社内向け（暫定メンテ動線あり） | internal のみ |
| **`/vendor/stock`** | 業者向け倉庫在庫一覧（参照のみ） | vendor のみ |

- 社内は `/vendor/stock` に**アクセス不可**（Q-F=B）。動作確認は internal を vendor に切り替えるテスト用ユーザーで行う

### 5-2. 表示要素（最小）

| 要素 | 内容 |
|------|------|
| 商品名 | `products.name` |
| 規格・サイズ | `products.spec`（あれば） |
| 単位 | `products.unit` |
| 在庫数 | `stock_items.quantity`（`location='center'` のみ） |
| 検索 | 商品名の partial match |
| 並び替え | 自分の担当現場の `site_products.display_order` で上位優先 |
| **「依頼する」ボタン** | 各商品行に配置（Q-E=A）。クリックで `/requests/new?product_id=...` へ |

### 5-3. 「依頼する」ボタンの動作

- ボタンクリック → `/requests/new?product_id=<選んだ商品>` へ遷移
- `/requests/new` 側で `product_id` query を初期選択値として読み込み
- 現場は通常どおり業者が選択（プルダウン）。業者の場合は自分の担当現場だけが選択肢に出る（RLS で絞られる）

### 5-4. 含めない要素（推測実装防止）

- 価格・原価・最終仕入日
- 移動履歴・ledger 表示
- 他現場の在庫情報
- 貸出在庫・リース在庫の数
- 残少アラート・通知

## 7. RLS 段階移行計画（確定）

### 7-1. 順序

| Step | 内容 | リスク |
|:----:|------|--------|
| **S1** | Supabase Auth 有効化、`app_users` テーブル、login 画面、middleware 追加 | 低（DB に触らない） |
| **S2** | 全テーブルに `authenticated` 用ポリシー追加（anon と同等の許可で並走） | 低 |
| **S3** | Server Action / page.tsx を**ログイン前提**に切替（`requested_by` 等に user_id を入れる） | 中 |
| **S4** | `vendors` / `vendor_sites` テーブル追加、業者ユーザーを 1 件登録して動作確認 | 中 |
| **S5** | 業者向け画面 `/vendor/stock` 実装、`/requests/new` の product_id query 対応 | 中 |
| **S6** | テーブル単位で **anon ポリシー縮小**：① 監査ログ → ② マスタ → ③ stock 系 → ④ requests | 中 |
| **S7** | `authenticated` ポリシーをロール別に分割（internal / vendor）、vendor は現場絞り込み | 高 |
| **S8** | anon ポリシー削除、GRANT も剥奪 | 低 |

### 7-2. ロールバック戦略

- S6 / S7 は **1 テーブル = 1 migration** で分離（例: `010_rls_audit_logs.sql`, `011_rls_master.sql`, `012_rls_stock.sql`, `013_rls_requests.sql`）
- 切り戻し: 該当 migration を逆順で `drop policy ...; create policy ... using (true) ...;` に戻す

### 7-3. policy 例（参考・S7 段階）

```sql
-- 業者は自分の担当現場のみ参照可
create policy "sites_vendor_select" on public.sites for select to authenticated
using (
  exists (
    select 1 from public.app_users u
    where u.id = auth.uid()
      and (
        u.role = 'internal'
        or (
          u.role = 'vendor'
          and exists (
            select 1 from public.vendor_sites vs
            where vs.vendor_id = u.vendor_id
              and vs.site_id = sites.id
          )
        )
      )
  )
);
```

→ 実装時の参考。`docs/02` B5 等の運用詳細が確定してから最終形に。

## 13. A-6 anon 段階削除（設計・影響範囲・2026-05-27）

**ステータス**: 設計確定（実装未着手）  
**スコープ**: 未ログイン（Supabase `anon` ロール）での DB アクセスを段階的に廃止し、アプリを **authenticated 前提**に移行する。  
**スコープ外（A-7 に分離）**: vendor 現場絞り込み RLS、`requested_by` による依頼可視制限、internal 専用ボタン非表示、`/vendor/stock` ホーム導線のロール分岐。

### 13-0. 前提（混同しやすい点）

| 用語 | 意味 |
|------|------|
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | **公開 API キー名**。ログイン後も SSR クライアントはこのキー + **セッション JWT** で接続する（キー名は変えない） |
| Supabase ロール `anon` | **未ログイン**時に PostgREST / RLS が適用される DB ロール |
| Supabase ロール `authenticated` | **ログイン後** JWT 付きで適用されるロール（A-2 で anon 同等ポリシー並走済み） |

### 13-3. 「今 anon を消すとどこが壊れるか」（一括削除シミュレーション）

**前提**: middleware 未導入（現状）で、全テーブル + 全 RPC の anon policy / EXECUTE を同時に削除した場合。

| 層 | 症状 |
|----|------|
| **未ログインユーザー** | ほぼ全画面で「読み込みエラー」「permission denied」。Server Action 送信も失敗 |
| **ログイン済み（internal / vendor）** | **基本的に壊れない**（authenticated policy / GRANT は A-2 で並走済み） |
| **例外リスク** | `app_users` 未登録でも業務テーブルは authenticated で通る。`get-current-user` の role 表示のみ null |
| **UAT** | 「ログインなしで触る」手順は **不可**になる（意図どおり） |

**ログイン済みなのに壊れるケース**（A-6 では起きにくいが確認項目）:

- migration 適用漏れで authenticated policy が無いテーブルがある
- RPC の `grant execute ... to authenticated` 漏れ
- セッション cookie が無効（middleware 導入後は `/login` へ）

### 13-4. vendor / internal の責務（A-6 vs A-7）

| 領域 | A-6（authenticated 化のみ） | A-7（RLS + UI） |
|------|---------------------------|-----------------|
| 出庫依頼 **作成** | vendor / internal ともログイン必須。DB は全件見えるまま | vendor は担当現場のみ、依頼は自分が登録したもののみ表示 |
| 出庫依頼 **受付・出庫** | UI 上は vendor にもボタン表示のまま（現状）。ログイン必須化のみ | internal のみ実行可（Action guard + UI 非表示） |
| 出庫依頼 **キャンセル** | 同上 | vendor は requested かつ自分の依頼のみ |
| `/stock` vs `/vendor/stock` | 両方ログイン必須。vendor も `/stock` に URL 直打ち可能（現状） | internal のみ `/stock`、vendor は `/vendor/stock` |
| マスタ CRUD | vendor もログイン後は操作可能（現状） | vendor は参照のみ or 不可 |

→ **A-6 では request flow の状態遷移ロジックは変えない**。壊すのは「未ログインで通っていた経路」だけ。

**原則**: 「**アプリでログイン必須化（middleware）→ DB で anon 縮小**」を **同じサブフェーズ内**でセットにする。DB だけ先に削ると未ログイン時に真っ白な画面 + permission denied が残る。

| サブフェーズ | アプリ | DB（1 migration = 1 テーブル群・rollback 可） |

| **A-6-1** | middleware: 未認証 → `/login?next=...`（`/login`, `/auth/signout` は除外） | **変更なし**（ログイン済み回帰確認） |
| **A-6-2** | 同上 | `audit_logs` の anon policy 削除 + anon GRANT 剥奪 |
| **A-6-3** | 同上 | マスタ群: `customers`, `products`, `sites`, `site_products` |
| **A-6-4** | 同上 | 在庫系: `stock_items`, `stock_ledger` + `apply_stock_movement` anon EXECUTE 剥奪 |

### 13-10. rollback しやすい進め方

1. **migration はテーブル群ごとに分割**（`011`〜`014`）。各ファイル末尾に `create policy ... to anon` の復元 SQL をコメントで同梱。

### 13-12. 認証（authentication）と認可（authorization）の分離（設計原則）

A-6 / A-7 を整理するうえで、**「ログインできているか」と「その画面・操作を許可されているか」は別概念**として扱う。実装上もレイヤを分ける。

#### 13-12-1. 用語

| 概念 | 英語 | 判定材料 | 失敗時 |
|------|------|----------|--------|
| **認証** | authentication (authN) | Supabase Auth セッション（cookie/JWT） | `/login` に戻す |
| **認可** | authorization (authZ) | `app_users.role`、`vendor_sites`、画面 ID | 「権限がありません」 or 404、UI 非表示 |

両者を混ぜると「ログイン障害が認可エラーに紛れる」「権限変更でセッションを切る必要がある」等の事故が起きやすい。

#### 13-12-2. ユーザー状態の分類

| 状態 | auth.users | app_users | role | 期待挙動（A-6-1 時点） | 将来（A-7 以降） |
|------|:----------:|:---------:|------|------------------------|-------------------|
| (a) 未認証 | ❌ | ❌ | — | `/login` へ | 同左 |
| (b) 認証済・app_users 未登録 | ✅ | ❌ | null | **ログイン許可・全画面到達可** | 「権限なし」画面で停止 or `/login` へ強制ログアウト（要決定）|
| (c) authenticated + role=internal | ✅ | ✅ | internal | 全画面到達可（現状どおり） | 全画面・全操作可 |
| (d) authenticated + role=vendor | ✅ | ✅ | vendor | 全画面到達可（現状どおり） | `/vendor/stock` と自分の依頼のみ |

A-6-1 では (b) を許可する（**認証のみで判定**）。(b) を弾くのは A-7 の責務。

#### 13-12-3. レイヤ別の責務

| レイヤ | 何を判定するか | 何を判定しないか |
|--------|----------------|------------------|
| `middleware.ts`（A-6-1） | 認証されているか | role、現場、操作可否 |
| Server Action（A-7） | 操作レベルの認可（例: vendor の cancel は自分の依頼のみ） | 認証（middleware で済んでいる前提） |
| RLS policy（A-7 / A-6 後半） | DB レベルの可視範囲（`vendor_sites`, `requested_by`） | UI 表示制御 |
| UI（A-7） | ロール別のリンク・ボタン表示 | DB の安全性（RLS が最終防衛線） |

#### 13-12-4. A-6-1 での実装的な線引き

- `middleware.ts` は **`user` の有無**だけを見る（`app_users` を join しない）。
- `lib/auth/get-current-user.ts` で取得する `role` は **UI 表示用情報**として扱う（A-6-1 時点では出し分けに使わない）。
- `lib/auth/get-actor-id.ts` は **追跡用**であり認可ではない（A-3 設計どおり）。
- 認可ヘルパ（例: `requireInternal()`、`requireVendorOwnedRequest(id)`）は **A-7 で導入**し、Server Action 冒頭で呼ぶ設計に統一する。
