# 店舗スカウト・プロフィール・通知・チャット

## 利用の流れ

1. 店舗は `/managers/settings` で店舗を選択・追加し、勤務地と時給を設定。
2. `/companies` でワーカーを検索。日時、希望エリア、業態、ポジション、経験年数、店長認証で絞り込める。
3. スカウトの勤務日、同日内の開始・終了時間、休憩時間、仕事内容を入力。
4. 確認画面で「時給 × 実働予定時間」「店舗負担の手数料20％」「合計」を確認して送信。
5. ワーカーは `/workers/scouts` で店舗の提示額を確認し、承諾または辞退。
6. 承諾したスカウトだけ、店舗・ワーカー双方のチャットが開く。勤務予定への追加と返信通知も同時に保存。
7. スカウト経由の勤務に出勤記録が付くと、プロフィールのシフルン勤務回数に反映。

ワーカーは求人検索や時給設定をしない。プロフィールでは名前・経験・スキル・自己紹介・働きたいエリアを編集する。

## 金額

- 店舗の時給 ×（終了−開始−休憩）の分数 ÷ 60 を1円単位で四捨五入し、ワーカーへの提示額とする。
- 手数料は提示額の20％を1円単位で四捨五入。店舗の合計は提示額＋手数料。ワーカーへの提示額から差し引かない。
- 例：時給1,200円、10:00〜15:00、休憩30分 → 実働4.5時間、提示額5,400円、手数料1,080円、店舗合計6,480円。
- 送信時点の時給・提示額・手数料率・手数料・店舗合計をDBに保存。後で店舗時給を変更しても送信済みスカウトは変わらない。
- 確認中に店舗の時給が変わった場合は、再確認を求めて送信を止める。計算はサーバーとDBでも検証。
- 表示は予定の基本額。交通費・手当・別途税額計算・決済・請求処理は含まない。
- 手数料20％は `lib/utils/matching.ts` の定数と014のDBトリガーで定義。変更時は両方を更新し、金額テストを実行する。

## 勤務回数と表示順

- 対象は `accepted` のスカウトに紐付き、当日以前の `attended` 記録がある勤務。同じスカウトは重複行があっても1回。通常の自店シフトや単なる承諾・閲覧回数は含めない。
- 回数は出勤の自己記録を基に集計し、給与支払いや退勤完了を保証する値ではない。編集できる自己申告の回数欄は設けない。
- 日時検索では空き時間の一致を最優先。確定済み勤務が重なる人は除外。
- 同条件の人を日替わりで回転させ、5人単位で先頭1枠を日替わり枠として確保。残り最大4人だけ勤務回数で並べる。最大3つの位置移動に抑える。
- 優遇は5回で頭打ち。6回以上の差でさらに順位を上げない。候補が2人の場合は日替わり枠と実績優遇の日を交互に設ける。

## 通知・チャット

- 通知：新規スカウト、承諾／辞退、相手からの新着メッセージ。未読件数と既読保存。直近100件を表示。
- 通知・スカウト一覧は画面表示中に15秒間隔、チャットは8秒間隔で更新。メール、SMS、OSのプッシュ通知は送信しない。
- チャットはスカウトごと。最初の50件と過去履歴の追加読み込みに対応。本文は2,000文字まで。画像・添付ファイルは未対応。
- 読み取り・送信アクションで参加者と承諾状態を確認。DBトリガーでも承諾前／辞退後のメッセージ挿入を拒否する。
- 返信処理はDB関数で実行し、承諾と勤務枠と通知をまとめて保存。同じ承諾を繰り返しても勤務枠・通知が増えない。返信済みの承諾／辞退は変更しない。
- メッセージには再送識別子を付け、通信失敗後の同一メッセージ再送を重複保存しない。
- Auth/RLSは従来の保留方針のまま。端末上のワーカー・店舗選択はログインではなく、参加者IDによるチェックは認証の代替ではない。

## SQL適用とリリース

追加ファイル：`supabase/migrations/014_matching_profiles_chat_notifications.sql`

1. 対象DBに001〜008、010〜013が適用済みであることを確認する（009は欠番）。既存SQLは再実行しない。
2. 検証用Supabaseで014を一度実行し、下記の手動確認を行う。
3. アプリの新しい送信処理と014を同じリリースで切り替える。014適用後は店舗ID・時給・手数料率を送らない旧版のスカウト送信は使えないため、旧版との併用を避ける。
4. 実DB適用前にバックアップを用意する。014はトランザクション内で実行され、既存テーブル・旧カラムの削除や既存データの名寄せは行わない。

この実装作業では実SupabaseへのSQL適用・本番デプロイは実施していない。
以前のスカウトで `store_id` が未設定の場合、店舗に推測で紐付けない。未返信の旧スカウトを承諾するには店舗から再送が必要。既に承諾済みの旧スカウトも店舗情報がなければチャットは開かない。

## 手動確認

- `/managers/settings`：店舗追加、既存店舗の選択、時給保存。
- `/workers/mypage`：希望エリア・スキル保存、出勤記録に応じた回数表示。時給入力欄がないこと。
- `/companies`：店舗側の条件検索、該当なし表示、勤務実績付きカード。
- `/companies/workers/[id]/scout`：自動計算→金額確認→戻って修正→送信。戻った際に入力が保持されること。
- `/workers/scouts`：ワーカーには基本提示額が表示され、承諾／辞退できること。
- `/managers/scouts`：返信状態と送信時の手数料込み合計の確認。
- `/workers/chat/[scoutId]`、`/managers/chat/[scoutId]`：承諾前と辞退後の直URLでは会話が開かず、承諾後は双方で送受信できること。
- 双方の `/notifications`：新着、未読、既読、該当スカウト／チャットへの遷移。
- 今日のスカウト勤務を出勤打刻し、プロフィールで1回増えること。二重操作で増えないこと。

## ローカル検証

```powershell
npm run lint
npm run build
node --test --test-isolation=none tests/matching.test.mjs tests/store-self-registration.test.mjs
```

SQLとアクションの検証には、一時フォルダに `@electric-sql/pglite` を入れて `PGLITE_MODULE` にその `dist/index.js` の絶対パスを設定する。アプリの依存定義に追加する必要はない。

```powershell
node tests/matching-db.mjs
# 別ターミナルで、テスト用ローカルDB APIを起動（127.0.0.1:55170）
node tests/local-matching-server.mjs
# ローカルAPIへ実際のサーバーアクションを接続して確認
node tests/matching-actions.mjs
```

検証用スクリプトは `.env.local` を読まず、メモリ内DBのみを使う。ローカルAPIは検証用に必要なPostgREST操作だけを実装したもので、本番サーバーとしては使わない。
