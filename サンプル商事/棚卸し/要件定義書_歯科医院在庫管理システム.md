## 2. プロジェクト背景

【確定】

- 貴社は複数の歯科医院を運営する法人。各医院で在庫管理・使用管理・発注管理・入荷管理が**個別に**行われている。
- 現状、**3か月に1回**、各医院のスタッフが**約5時間**かけて商品数を確認し、スプレッドシートへ手入力している。
- 棚卸し作業は**診療を止めて複数スタッフで対応**しており、業務負担が大きい。
- 日常の使用状況がスプレッドシートへ反映されるまで時間がかかり、**現在庫を正確に把握できていない**。
- 発注後に使用されず滞留する商品、使用期限切れによる廃棄が発生している。
- 理事長は、**多少の数量誤差は許容**するが、**決算時に在庫資産額を算出できる程度の精度**で、法人全体および医院別の在庫を把握したいと考えている。

## 3. 現状の課題

【確定】

| No | 課題 | 影響 |
|---|---|---|
| 1 | 棚卸しが3か月に1回・約5時間・複数スタッフ・診療停止 | 人件費・機会損失・スタッフ負担が大きい |
| 2 | 使用状況の反映に時間がかかる | 現在庫をリアルタイムに把握できない |
| 3 | 医院ごとに管理が分散 | 法人全体の在庫・資産額を横断的に把握できない |
| 4 | 発注後に滞留する在庫が発生 | 過剰在庫・資産の固定化 |
| 5 | 使用期限切れによる廃棄 | 廃棄ロス・コスト増 |
| 6 | 手入力による表記揺れ・重複 | データ精度の低下 |

## 4. システム化の目的

### 4.1 MVPの目的【確定】

1. 日常の使用状況を在庫数へ反映する。
2. 医院別・商品別の現在庫を確認できるようにする。
3. 発注が必要な商品を確認できるようにする。
4. 発注済み商品と未入荷数量を管理する。
5. 入荷時に現在庫へ反映する。
6. 医院別および法人全体の在庫資産額を算出する。
7. 既存の3か月ごとの棚卸し作業を削減する。

### 4.2 MVPに含めないもの（本目的から除外）【確定】

- 3か月ごとの実棚卸し専用画面
- 理論在庫との差異入力
- 棚卸し補正機能

> 上記は第23章「将来拡張案」で整理する。

## 7. 利用者と権限

### 7.1 想定利用者【確定】

| 利用者 | 主な役割 |
|---|---|
| 医院スタッフ | QRカードの読取・使用登録 |
| 発注担当者 | 発注候補の確認・発注登録・入荷登録 |
| 管理者 | 全体の在庫・資産額の確認、マスタ管理 |

### 7.2 認証方式【確定】

- MVPでは**複雑なログイン・権限管理を行わない**方針。
- **医院別URL**（医院ごとにアクセスURLを分ける）を採用する。GAS Webアプリは1つのURLしか発行できないため、医院ごとのURLは**共通URLにクエリパラメータ（例：`?clinic=NIS`）を付与したブックマーク**として配布する形で実現する。
- **例外**：iPhone等の標準カメラでQRコードを直接読み取る「即時使用」画面（第10.4b・14章参照）は、QR自体に医院情報を含められない（第14章の決定）ため、上記の医院別URLの仕組みが使えない。この画面に限り、**初回アクセス時に医院を選択し、以後は端末（ブラウザ）に記憶**する方式で医院を特定する。
  - 共有端末で医院を誤って設定した場合に備え、画面上に「医院を変更する」導線を設ける（確認ダイアログつき）。
- 追加のセキュリティ強化案【今後検討】：URLを第三者に推測されにくくするため、医院IDではなく十分な長さのランダムな文字列をURLに含める。加えて、共有端末からのアクセスを想定し、簡易PIN（暗証番号）の入力を組み合わせることも将来的に検討可能（MVPでは必須としない）。
- 【要確認】現状、Webアプリのアクセス範囲は開発者本人のみ（限定公開）に設定している。スタッフ・発注担当者が実際に使用するには、公開範囲を広げる設定変更が必要（第22章参照）。

### 7.3 権限マトリクス【確定】

各利用者の操作範囲を以下のとおり確定する。

| 操作 | 医院スタッフ | 発注担当者 | 管理者 |
|---|---|---|---|
| QR読取・使用登録 | ○ | ○ | ○ |
| 在庫一覧の閲覧 | ○（自医院のみ） | ○（全医院） | ○（全医院） |
| 発注候補の確認・発注登録 | − | ○ | ○ |
| 入荷登録 | − | ○ | ○ |
| 在庫の手動修正 | − | − | ○ |
| 使用・入荷登録の取消／修正 | − | ○ | ○ |
| ダッシュボード閲覧 | ○（自医院分） | ○（自医院分） | ○（全医院） |
| 商品・医院マスタの編集 | − | − | ○ |
| 担当者マスタの編集 | − | − | ○ |

> 在庫の手動修正は誤操作・データ不整合のリスクが大きいため、管理者のみに限定する。発注担当者は使用・入荷登録の取消・修正（第10.11参照）は行えるが、在庫数の直接書き換えは行えない。

## 8. システム構成

### 8.1 技術構成【確定】

| 要素 | 採用技術 |
|---|---|
| アプリケーションロジック | Google Apps Script（GAS） |
| データストア | Googleスプレッドシート |
| 画面（UI） | GAS HTML Service |
| 利用端末 | スマートフォン対応Webアプリ（iPhone / Android の主要ブラウザ） |
| QR読取 | スマートフォンのカメラを利用したQRコード読取 |
| 初期データ移行元 | 既存のExcelまたはスプレッドシート |

### 8.2 データ構造方針【確定】

- 既存表を**そのままデータベースとして使用しない**。
- システム内部では**縦型（正規化された）テーブル構造**へ変換して管理する。
- 医院別に横並びの在庫情報は、1行1レコードの縦型へ変換する。

### 8.3 構成イメージ

```
[スマートフォンブラウザ]
        │ （HTTPS）
        ▼
[GAS HTML Service（画面）]
        │
        ▼
[Google Apps Script（業務ロジック／排他制御）]
        │
        ▼
[Googleスプレッドシート（データストア：縦型テーブル）]
```

## 9. 業務フロー

### 9.1 基本運用フロー【確定】

```
1. 新しい箱または袋を開封する
2. 対象商品のQRカードを所定のケースへ入れる
3. 1日の業務終了時に、ケース内のQRカードをスマホでまとめて読み取る
4. 同一商品のQR読取回数を使用数量として集計する
5. 登録内容を確認し、使用登録を確定する
6. 確定数量だけ現在庫を減算する
7. 発注基準以下の商品を発注候補として表示する
8. 担当者が発注商品と数量を登録する
9. 発注時点では現在庫へ加算せず、発注済み未入荷数量として管理する
10. 商品到着後、担当者が入荷数量を登録する
11. 入荷確定時に現在庫へ加算する
```

### 9.2 重要な管理区分【確定】

- 「**実際に医院内に存在する現在庫**」と「**発注済みだが未入荷の数量**」は、**別項目**として管理する。

### 9.3 管理方式による運用の分岐【確定】

第9.1の基本フローは、**箱・袋単位で数量を数えられる商品**（＝「数量管理」商品）を前提としている。

一方、以下のような商品は、開封後に少しずつ使用され、残量の目視確認によって発注タイミングを判断する運用となっており、QR読取回数による数量管理になじまない。

- シタネスト（残り5本で1箱発注）
- スーパーボンドポリマー粉末（残り1/3で1つ発注）
- プロビナイス粉A3（小瓶へ補充、大瓶が空になったら1つ発注）
- 歯科用注射針27G（残量1/3で1つ発注）
- テガダーム（残り20枚で1つ発注）

これらのように、**数量を都度数えるのではなく「発注が必要になったタイミング」を管理する商品**を区別するため、**医院別在庫に「管理方式」という属性**を設け、医院・商品の組み合わせごとに以下いずれかを設定する。

| 管理方式 | 対象商品の例 | 運用 |
|---|---|---|
| 数量管理 | グローブ、コットン等、箱・袋単位で数えやすい商品 | 第9.1の基本フローどおり。QR読取結果を使用数量として集計し、現在庫を加減算する |
| 発注トリガー管理 | シタネスト、スーパーボンド、プロビナイス、注射針、テガダーム 等、残量目視・補充で運用する商品 | 第9.4のフローに従う。現在庫数は数値管理せず、「発注が必要になったサイン」をQR読取で登録する |

> **【確定】管理方式は医院共通ではなく、医院ごとに個別設定する。** 各医院の来客状況・在庫の置き方によって、同じ商品でも管理方式が異なりうるため（貴社ヒアリング回答による）。例えば同じグローブでも、A医院では箱単位の数量管理、B医院では残量による発注トリガー管理、という設定が可能。
>
> 管理方式を分けることで、すべての商品を同一ルールで管理する必要がなくなり、現場の実運用に即した仕組みとなる。この設計変更に伴う機能面の詳細は第10.4a章、データ面の詳細は第12.2章を参照。

### 9.4 発注トリガー管理商品の運用フロー【確定】

発注トリガー管理商品は、QRカードの読取という操作自体は数量管理商品と共通にしつつ、その意味づけを変える。

```
1. 商品ごとに定められた発注トリガー条件（残量・補充状況等）に、
   スタッフが目視で気づく
2. 対象商品のQRカードをスマートフォンで読み取る
3. システムは「使用数量の記録」ではなく「発注が必要になった合図」として扱う
4. 読み取られた商品は、現在庫数の増減を行わず、発注候補一覧へ即時に追加される
5. 発注担当者が発注候補一覧を確認し、通常どおり発注登録を行う
6. 入荷後は、発注管理・入荷履歴に沿って通常どおり入荷登録を行う
```

- 発注トリガー管理商品は、**現在庫数を精緻な数値としては保持しない**（在庫一覧では「管理対象外」と表示する）。
- 発注・入荷・未入荷数量の管理（第16章）は、数量管理商品と同じ仕組みをそのまま利用する。
- QRカードは商品ごとに1枚で運用する（同一商品を1日に複数回読み取っても、複数回発注登録されないよう、当日中の重複読取は1件の発注候補としてまとめる）。

### 9.5 フロー図（状態の流れ）

以下は数量管理商品のフロー。発注トリガー管理商品のフローは第9.4参照。

```
[開封] → QRカードをケースへ
                 │
         （1日の終わり）
                 ▼
   [QR読取] → [集計] → [確認] → [使用登録確定]
                                      │
                                      ▼
                              現在庫を減算
                                      │
                    在庫 ≤ 発注基準 なら発注候補へ
                                      ▼
                          [発注登録] → 未入荷数量に加算
                                      │
                          （商品到着）
                                      ▼
                          [入荷登録] → 現在庫に加算／未入荷数量を減算
```

### 9.6 QR読取の2つの運用パターン【確定】

QRコードの読取方法として、以下の2パターンを用意し、医院の運用に応じて使い分けられるようにする。

| パターン | 読取手段 | タイミング | 数量の入力方法 |
|---|---|---|---|
| A：まとめ読取 | アプリ内カメラ（QR読取画面） | 1日の終わりにまとめて | 1回読み取った後、**画面上で数量を＋／－調整**（案B。第14.1参照） |
| B：即時読取 | スマートフォンの**標準カメラ**アプリ | 使用の都度、その場で | 数量入力の画面を出さず、**1回の読取＝1個の使用として即時処理**。複数個使用した場合は、同じQRカードを使用数分だけ繰り返し読み取る |

- パターンBは、専用アプリを開く手間を省き、標準カメラで読むだけで作業を完結させたいという運用ニーズに対応するために追加した（第10.4b参照）。
- どちらのパターンも、同じQRカード（商品ごとに1枚）をそのまま使用できる。パターンBで複数個使用する場合も、**物理的なQRカードを複数枚用意する必要はなく**、同じカードを続けて読み取ればよい（第14.3参照）。
- 医院ごと、あるいはスタッフごとに、どちらのパターンを使うかは自由に選べる（両方の併用も可能）。

### 9.7 医院の特定方法【確定】

- パターンA（アプリ内カメラ）：画面で医院を選択する、または医院別URL（第7.2参照）のクエリパラメータから自動判定する。
- パターンB（標準カメラ・即時読取）：QRに医院情報を含められないため、**初回アクセス時にスタッフが医院を選択し、以後はその端末（スマートフォン）に記憶**する。医院ごとに端末を固定して運用することを前提とする。
- 共有端末を使う場合の医院誤設定リスクに備え、画面上から医院設定をいつでも変更できるようにする（変更時は確認ダイアログを表示）。

## 10. 機能要件

各機能を「機能名／目的／利用者／入力／処理／出力／正常系／異常系／権限制御／保存データ／関連シート／受入条件」で記載する。
権限制御は第7.3の権限マトリクスに準拠する（確定済み）。

### 10.1 商品マスタ管理

QR札の印刷運用【2026-08-21ヒアリング確定】：
- QR面を印刷後、同じ検索・並び順のまま「写真面」へ切り替えて両面印刷する。
- 商品写真が未登録の場合、写真面には「写真未登録」と表示する。現場のスマートフォンから撮影または端末内の写真を選んで登録する。
- 発注基準は医院ごとの値を使用する。数量管理では0以上の整数、発注トリガー管理では「残り1箱」「補充用の箱を開封したとき」等の条件文を入力する。
- 医院が指定されていない全医院表示では、発注基準の入力・表示を行わない。

### 10.4 QR読取・使用登録（パターンA：アプリ内カメラ・まとめ読取）

| 項目 | 内容 |
|---|---|
| 機能名 | QR読取・使用登録 |
| 目的 | 使用した商品をQR読取結果から商品別に集計し、在庫へ反映する（数量管理商品が対象。発注トリガー管理商品は第10.4a参照。標準カメラでの即時読取は第10.4b参照） |
| 利用者 | 医院スタッフ |
| 入力 | QRコードの読取（商品ID）、画面上での数量の増減・修正、誤読取商品の削除 |
| 処理 | ①QRを1回読み取り、商品を画面に追加 → ②画面上で数量を＋／－ボタン等により入力・修正（**案B確定**：同一商品を複数使用した場合も、同じQRの再読取ではなく画面上の数量操作で入力する） → ③確認 → ④確定時に一連処理（後述10.5）を実行 |
| 出力 | 読取商品名、商品別数量、確認画面、確定結果 |
| 正常系 | 読取→数量入力→確定→在庫減算が完了する |
| 異常系 | 未登録QR、通信エラー、二重送信は処理を確定させない／エラー表示 |
| 権限制御 | 医院スタッフ（自医院のみ） |
| 保存データ | 使用履歴（第10.5参照） |
| 関連シート | 医院別在庫、使用履歴、商品マスタ |
| 受入条件 | 確定した使用数量どおりに集計・減算され、二重送信・誤読取が防止される |

QR読取画面に必須の要素【確定】：
- 読取した商品名／商品別の数量表示／数量の＋・－ボタンによる増減・手動修正／誤読取商品の削除／登録前の確認／一括確定／同一QRの意図しない連続読取防止（第14.2）／確定処理の二重送信防止／読取成功時のフィードバック（画面表示・音・振動など）

> QRカードは商品ごとに1枚で運用する。1日に同じ商品を複数箱開封した場合も、QRは1回読み取り、その後の画面操作で数量を「2」等に修正すればよいため、複数枚の物理カードは不要（第14章参照）。

### 10.4b 即時使用登録（パターンB：標準カメラ・即時読取）【確定】

| 項目 | 内容 |
|---|---|
| 機能名 | 即時使用登録 |

| 異常系 | 未登録QR・管理方式未設定の商品はエラー表示。短時間の再読取・画面再読み込みによる二重処理は防止する |

> パターンA（10.4）とパターンBはどちらも同じQRカードを使う。数量の入力方法だけが異なる（Aは画面操作、Bは読取回数そのもの）。医院やスタッフの好みでどちらを使ってもよい。

| 保存データ | 入荷ID、発注ID、医院、商品、入荷数量、入荷日、登録者、登録日時、登録前在庫、登録後在庫（発注トリガー管理商品は「対象外」） |
| 関連シート | 入荷履歴、発注管理、医院別在庫 |
| 受入条件 | 数量管理商品は入荷登録で在庫が正しく加算され、発注状態が更新される。**発注トリガー管理商品も、在庫を操作せずに発注を「入荷済み」として完了できる**（Codexコードレビューで指摘された不整合の修正事項） |

### 10.10 在庫資産額算出

| 機能名 | 在庫資産額算出 |
| 目的 | 決算時に算出できる程度の精度で資産額を把握する |
| 利用者 | 管理者 |
| 入力 | （在庫データと評価単価を自動集計） |
| 処理 | 数量管理商品：在庫評価額 ＝ 評価単価（**税込**、第15.3参照）× 現在庫数 を集計。評価単価未設定の商品は**0円として集計**する。発注トリガー管理商品は現在庫数を数値管理しないため、**資産評価額の集計対象外**とする |

| 正常系 | 各単位の合計が表示される |
| 異常系 | 評価単価未設定商品・発注トリガー管理商品は、それぞれ一覧に明示し、合計金額から誤解が生じないようにする |
| 権限制御 | 管理者 |
| 保存データ | （参照のみ／算出結果） |
| 関連シート | 医院別在庫、商品マスタ |
| 受入条件 | 各集計単位で資産額が算出できる |

### 10.11 使用登録・入荷登録の取消・修正

| 項目 | 内容 |
|---|---|
| 機能名 | 使用登録・入荷登録の取消・修正 |
| 目的 | 誤登録があった場合に、履歴を保持したまま在庫を正しい状態に戻す |
| 利用者 | 発注担当者、管理者 |
| 入力 | 取消・修正対象の履歴（使用履歴／入荷履歴）、取消理由 |
| 処理 | 対象の履歴レコードを直接書き換えるのではなく、**取消記録を追加**して現在庫を元に戻す（例：使用登録の取消であれば、取り消した数量分だけ在庫を加算する取消レコードを追加）。入荷登録の取消も同様に、加算した数量を減算する取消レコードを追加する |
| 出力 | 更新後在庫、取消履歴 |

| 受入条件 | 取消操作によって履歴が削除されず、取消の経緯が追跡できる |

### 10.12 在庫手動修正

| 項目 | 内容 |
|---|---|
| 機能名 | 在庫手動修正 |
| 目的 | 数え間違いや登録漏れがあった場合に、在庫数を直接修正する |
| 利用者 | 管理者 |

未導入部門との一時的な貸し借り運用【2026-08-21ヒアリング確定】：
- 相手部門が本システムをまだ利用しておらず、移動先在庫へ登録できない期間に限り、「訂正・取消」画面の在庫手動修正を使用する。

## 14. QRカードの運用

【確定】

| No | ルール |
|---|---|
| 1 | QRカードは商品ごとに**1枚**発行する（第14.3参照） |
| 2 | 使い捨てではなく再利用する |
| 3 | ケースへ入れるタイミングは「新しい箱または袋を開封した時点」（数量管理商品）／発注トリガー条件に気づいた時点（発注トリガー管理商品。第9.4参照） |
| 4 | QR1回の読取の扱いは、読取手段（パターンA／B）によって異なる（第14.1参照） |
| 5 | 読取結果を商品別に集計する |
| 6 | 読取後、QRカードは元の保管場所へ戻して再利用する |
| 7 | QRには商品を識別する情報のみを持たせる（第14.4参照） |

【確定】QRコードに医院・保管場所の情報は**含めない**。商品を医院間で移動する可能性があるため、QRは商品識別のみに用いる。医院の判別方法は、パターンA（アプリ内カメラ）は医院別URL、パターンB（標準カメラ）は端末記憶による（第7.2・9.7参照）。

### 14.1 複数使用時の入力方法【確定：読取手段により2方式】

同じ商品を複数使用した場合の入力方法は、第9.6で整理した読取パターンによって異なる。

| パターン | 入力方法 |
|---|---|
| A：アプリ内カメラ（まとめ読取） | **QRコードを1回だけ読み取り、画面上で数量を増減する（案B）** |
| B：標準カメラ（即時読取） | 画面での数量調整は行わず、**同じQRカードを使用数分だけ繰り返し読み取る**。1回の読取＝1個の使用として即時処理する |

- パターンAで「同じQRを使用数分だけ繰り返し読み取る」運用（いわゆる案A）を採用しないのは、意図した複数回読取と、カメラに映り続けたことによる誤読取をシステム側で区別できず、数量ずれの原因となるため（第14.2の誤連続読取防止とあわせて対応）。
- パターンBは、読み取るたびに1個ずつ即時反映する運用を優先し、確認画面を挟まない設計とした（第10.4b参照）。そのため、複数個使用した場合はカメラで同じカードを続けて読み取る操作になるが、**物理的なQRカードは1枚のままで対応できる**（第14.3参照）。

### 14.2 誤連続読取防止の仕様【確定】

以下は、主にパターンA（アプリ内カメラ）に適用する。

- 同一QRを読み取った後、**数秒間（例：2秒）は同じQRを再認識しない**（クールタイムを設ける）。
- **QRを一度カメラの外へ外してから再度映した場合のみ**、次の読取として認識する。
- 上記により、カメラに映り続けたことによる意図しない多重カウントを防止する。パターンAは案B（1回読取＋画面で数量入力）と組み合わせることで、数量の入力はすべて画面上の操作で行われるため、誤読取による数量ずれのリスクを最小化する。
- パターンB（標準カメラ）は、端末側のブラウザ・カメラアプリの仕様に準じる。同一QRを開いた直後の短時間の再読み込み（リロード等）による二重処理は、システム側の冪等処理（第10.4b・17章参照）で防止する。

### 14.3 QRカードの準備枚数【確定】

商品ごとに**1枚**で運用する（パターンA・Bいずれの読取方式でも共通）。

- 1日に同じ商品を複数箱・複数個使用した場合の懸念（例：グローブを1日に2箱以上開封する等）は、いずれのパターンでも、**物理的に複数枚のQRカードを用意する必要はない**。パターンAでは画面操作で数量を「2」等に修正し、パターンBでは同じ1枚のカードを続けて読み取ることで対応する。
- 保管場所が複数箇所に分かれている商品等、運用上どうしても複数枚が必要な場合は、商品マスタ上は同一商品IDとして扱い、QRカードのみ追加発行することで対応可能（同一商品IDのQRが複数枚存在しても、システム上の扱いは変わらない）。

### 14.4 QRコードの実装形式【確定】

- QRコードには、**WebアプリのURLに商品IDを付与した文字列**を埋め込む（例：`https://script.google.com/.../exec?p=P0001`）。
- これにより、専用のQR読取画面（パターンA）だけでなく、**iPhone・Androidの標準カメラアプリで読み取るだけ**でもWebアプリが起動し、使用登録が完結する（パターンB・第10.4b参照）。
- URLが読み取れない旧式の読取機に備え、従来形式（`INV-商品ID`）の解析にも対応する。

## 15. 在庫計算ルール

### 15.1 基本ルール【確定】

以下は**数量管理商品**に適用するルール。発注トリガー管理商品は現在庫数を数値管理しないため対象外（第9.4参照）。

| ルール | 内容 |
|---|---|
| 使用時 | 現在庫 −（使用数量 × QR1回あたり減算数量）。使用数量の入力方法はパターンA／Bで異なる（第14.1・9.6参照） |
| 発注時 | 現在庫は変更しない。未入荷数量 ＋ 発注数量 |
| 入荷時 | 現在庫 ＋ 入荷数量、未入荷数量 − 入荷数量 |
| 資産額 | 在庫評価額 ＝ 評価単価（税込）× 現在庫数 |

### 15.2 管理単位・管理方式【確定】

- 管理単位（箱・袋・個・本 等）は**商品ごと（医院共通）に設定**する。
- 1箱あたり入数・個数単位の管理方法は**現物確認とヒアリング後に商品ごとに確定**する（第18章の貴社ご対応事項）。
- 管理単位とは別に、**医院・商品の組み合わせごとに管理方式**（数量管理／発注トリガー管理）を設定する（第9.3・12.2参照）。管理単位は「何を数えるか」で医院共通、管理方式は「数えて減算するか、発注タイミングだけを管理するか」で医院ごとに異なりうる、という別軸の設定である。

### 15.3 在庫評価【確定】

- MVPでは「評価単価（税込）× 現在庫数」で算出する。ロット別・購入時期別の厳密評価はMVP対象外。
- 評価単価は**税込単価**を採用する。理事長・会計士の最終確認により変更となる場合は、単価の再入力で対応する。
- 評価単価が未設定の商品は**0円として集計**し、未設定商品の一覧を画面に表示することで入力漏れに気づけるようにする。
- 発注トリガー管理商品は、現在庫数を数値管理しないため、在庫評価額の集計対象外とする（第10.10参照）。

### 15.4 在庫がマイナスになる場合【確定】

- **マイナス登録を許容**し、在庫一覧・在庫詳細画面に**警告表示**する（0で止めない）。
- マイナスのまま記録することで、登録漏れ等の実態が見える化され、修正のきっかけとなる。

### 15.5 発注基準の優先関係【確定】

- 発注基準数は、**商品マスタに標準値**を持たせ、**医院ごとに個別値を設定した場合はそちらを優先**する（医院ごとに在庫基準が異なりうるため）。
- 医院別の値が未設定の場合は、商品マスタの標準値を使用する。

## 16. 発注・入荷の状態遷移

### 16.1 発注状態【確定】

| 状態 | 意味 |
|---|---|
| 発注済み | 発注登録済み・未入荷 |
| 一部入荷 | 一部のみ入荷 |
| 入荷済み | 全数入荷完了 |
| キャンセル | 発注取消 |

### 16.2 状態遷移図

```
        [発注済み]
        /    |    \
       ▼     ▼     ▼
 [一部入荷] [入荷済み] [キャンセル]
       │
       ▼
   [入荷済み]（残数入荷で完了）
```

### 16.3 MVP範囲【確定】

- 「一部入荷」および「発注キャンセル」は**MVPに含める**。分割納品に対応しないと未入荷数量が実態と合わなくなり、発注候補の判定にも影響するため。
- 発注登録を行わずに直接入荷登録する例外処理（急遽購入した商品等）は**必要**とし、対応する（第10.9参照）。
- 発注トリガー管理商品からの発注候補登録（第10.4a）も、通常の発注登録と同じ状態遷移で管理する。ただし**入荷登録は数量入力を伴わず、発注済みの数量を一括で「入荷済み」に更新する**（現在庫を持たないため。第10.9参照）。「一部入荷」は数量管理商品のみで発生する。

## 21. 前提条件・制約

【確定】

- 実装基盤はGAS＋Googleスプレッドシートであり、その性能・制約（実行時間・API呼び出し回数等）の範囲内で構築する。
- 多少の数量誤差は許容される（決算時に資産額を算出できる精度を目標とする）。
- 既存データの整理・現物照合は開発とは別作業であり、開発工数に含まれない。
- MVPでは複雑なログイン・権限管理を行わない。認証方式は医院別URL、権限は第7.3の権限マトリクスで確定済み。
- 管理方式（数量管理／発注トリガー管理）は**医院・商品の組み合わせごと**に割り当てる（第9.3・12.2参照）。同じ商品でも医院によって異なってよい。現物確認・ヒアリング後に医院ごとに確定する（第18.2参照）。対象範囲が出揃うまでは、発注トリガー管理商品の総数・実装ボリュームが確定しない点に留意する。
- 使用期限管理は、MVPでは**指定商品のみ**を対象とする（第22.1参照。対象商品の選定は今後のヒアリングによる）。
- 第22章に残る未確定事項が確定するまで、該当機能の詳細設計は保留する。

## 22. 未確定事項・次回ヒアリング項目

以下は、今回のヒアリングおよび実装検討の過程で新たに生じた**残存の要確認事項**のみを記載する。

| No | 分類 | 未確定事項 | 補足 |
|---|---|---|---|
| 1 | 管理方式 | 発注トリガー管理を採用する商品の対象リストと、医院・商品ごとの発注トリガー条件 | 例示（シタネスト、スーパーボンド等）は把握済みだが、対象範囲の全量は現物確認・ヒアリング後に**医院ごと**に確定する（第9.3・第18.2参照。管理方式は医院間で異なりうるため） |
| 2 | 使用期限管理 | 期限管理の対象とする「指定商品」の具体的な商品名 | MVPでは指定商品のみ管理する方針は確定（第22.1参照）。対象商品は未定 |
| 3 | 資産評価 | 評価単価（税込）の最終確認 | 現時点では税込で確定運用とするが、理事長・顧問会計士の最終確認待ち（第15.3参照） |
| 4 | 認証方式 | 医院別URLに加えて簡易PIN等を組み合わせるか | MVPでは医院別URLのみで運用可能（第7.2参照）。強化の要否は今後検討 |
| 5 | 認証・公開範囲 | Webアプリの公開範囲（アクセスできる利用者の範囲）を誰に広げるか | 開発・検証段階では開発者本人限定で構築している。スタッフ・発注担当者が実際に使用する前に、医院別URL運用とあわせて正式に決定・設定変更する必要がある（第7.2・7.3参照） |

| 8 | 訪問部データ移行 | 訪問部の商品と既存医院の商品マスタとの重複統合結果の最終確認 | 第18.5のとおり、完全一致した品目は自動的に商品マスタを共有する方針だが、移行実行後に貴社にて一致結果（一致した品目／新規登録した品目の一覧）を確認していただく必要がある |

### 22.1 使用期限管理（特記）【確定（範囲）／一部要確認（対象商品）】

- MVPでは**指定商品のみ**使用期限を管理する（③入荷・ロット単位ですべて管理する、は採用しない）。
- 対象商品の具体的な選定、入力方法（入荷登録時に期限日を入力する想定）の詳細は、対象商品リストの確定後にあわせて設計する。

## 24. 受入条件

【確定】MVP全体の受入条件

| No | 受入条件 |
|---|---|
| 1 | 商品マスタ・医院マスタ・医院別在庫を登録・参照できる |
| 2 | 商品ごとのQRを生成し、読取機能で正しく識別できる |
| 3 | QR読取により商品別の使用数量が集計され（入力方法は第14.1で確定。パターンA／Bいずれでも）、確定時に現在庫が減算される |
| 4 | 同一QRの誤連続読取・確定の二重送信が防止される |
| 5 | 医院別・商品別の現在庫を検索・絞り込みして確認できる |
| 6 | 現在庫と発注済み未入荷数量が別項目として管理される |
| 7 | 発注基準以下の商品が発注候補として表示される |
| 8 | 発注登録で未入荷数量が増え、現在庫は変わらない |
| 9 | 入荷登録で現在庫が加算され、未入荷数量が減り、発注状態が更新される |
| 10 | 使用・入荷の履歴（登録前後在庫を含む）が保存される |
| 11 | 商品別・医院別・法人全体・カテゴリ別の在庫資産額（税込単価ベース）が算出され、評価単価未設定商品・発注トリガー管理商品は一覧で明示される |
| 12 | 複数医院・複数スタッフの同時更新で在庫が競合しない |
| 13 | 同時更新が制御され、二重登録が防止され、エラー時はエラー内容が記録されて在庫と履歴の整合性が維持される |
| 14 | iPhone・Androidの主要ブラウザ実機で操作できる |
| 15 | 既存データを削除・上書きせず初期在庫を移行できる |
| 16 | 発注トリガー管理商品をQR読取すると、在庫数を変えずに発注候補へ登録される |
| 17 | 使用登録・入荷登録を取消記録の追加によって取り消せ、取消の経緯が履歴として残る |
| 18 | 管理者が理由入力とともに在庫を手動修正でき、管理者以外は修正できない |
| 19 | 第7.3の権限マトリクスどおりに各利用者の操作範囲が制限される |
| 20 | 医院ごとに発注基準を個別設定でき、未設定の場合は商品マスタの標準値が適用される |
| 21 | ダッシュボードが役割ごとに定められた表示項目・表示範囲で表示される（第11.1参照） |
| 22 | **管理方式・発注トリガー条件を医院ごとに個別設定でき、同じ商品でも医院間で異なる管理方式を設定できる**（第9.3・12.2参照） |
| 23 | **iPhone・Androidの標準カメラでQRを読み取るだけで、専用アプリを開かずに使用登録・発注トリガー登録が完結する**（パターンB。第10.4b参照） |
| 24 | 標準カメラでの読取時、初回に選択した医院が端末に記憶され、以後は自動的にその医院として処理される（第7.2・9.7参照） |
| 25 | **発注トリガー管理商品の入荷登録が、在庫を操作せずに発注状態を「入荷済み」へ更新する形で完了できる**（第10.9参照） |
| 26 | 発注登録が冪等トークンにより二重送信から保護される（同一の登録操作を再送しても二重登録されない。第17章参照） |
| 27 | **「訪問部」が既存医院と同様に、医院一覧・在庫管理・QR運用・ダッシュボード等すべての機能を利用できる**（第18.5参照） |

> 第22章に残る要確認事項（発注トリガー管理商品の対象リスト、使用期限管理の対象商品、Webアプリの公開範囲、初回棚卸し機能の設計、訪問部の重複商品確認結果等）に関わる受入条件は、各事項の確定後に追記する。
