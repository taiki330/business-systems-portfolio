## 1. 背景・目的

### 1-1. 背景

- 現行の在庫・発注・リース管理システム（A-ZiP 系）が 2028 年前後に利用継続困難となる見込み。
- リース品の一部がシステムに載らず、**Excel 併用**で管理されている。
- サンプル市Aセンターに加え、**関東（サンプル市B）・九州**でも実運用があるが、現行システムは 1 拠点前提。
- 現場からの返却数が出庫数を超える申告が常態化し、**実棚とシステム値が恒常的に食い違って**いた。

### 1-2. 目的

1. 在庫管理・オーダー（資材依頼）・入出庫・現場登録を現行と同等以上に行える。
2. リースを一元可視化し、Excel 併用を減らす。
3. **紙の「資材発注書」をシステムから出力**し、現場〜センター〜事務の紙運用をそのまま置き換える。
4. 在庫のズレの原因（過入庫・棚卸未実施・現完滅失の滞留）を機能として潰す。
5. 地域センターごとに「自分の地域の在庫だけ」を見られるようにする。

## 2. 利用者ロールと権限

### 2-1. ロール定義（実装値: `app_users.role`）

| ロール値 | 画面上の呼称 | 想定利用者 | 位置づけ |
|---------|-------------|-----------|----------|
| `admin` | 事務 | サンプル建設事務 | 全機能の管理者。マスタ・在庫補正・承認・分析 |
| `center` | センター | サンプル市A／サンプル市B／九州の各センター担当 | **原則参照専用**。例外は棚卸・出庫完了・ヤード積込日訂正・センター間移動 |
| `vendor` | 現場 | 各現場（1現場1アカウント） | オーダー起票と自現場の参照のみ |
| `internal` | （レガシー） | 移行期間の既存アカウント | `admin` 相当に正規化。新規発行しない |

**R-ROLE-01**: `app_users` に未登録（`role = null`）のログインは `/no-access` へ寄せ、機能を一切使わせない。
**R-ROLE-02**: `center` は `center_id` により**自分の地域センターのデータのみ**参照できる（migration 089）。
**R-ROLE-03**: `vendor` は `app_user_sites` により**担当現場のみ**参照・起票できる。1アカウントで複数現場を担当できる（migration 079）。

### 3-2. オーダー（資材依頼）〜 資材発注書

現行運用の「オーダー」は**P0 で実装した出庫依頼（`stock_requests`）と同一概念**である（D-20260801-07）。紙の資材発注書が「1オーダー番号の下に複数商品」であるのに対し、出庫依頼は単票だったため、`orders`（ヘッダー）＋ `stock_requests`（明細）の親子構造にした。

| ID | 要件 | 実装 |
|----|------|------|
| R-O-01 | 現場が1回のオーダーで**複数商品を同時に依頼**できる。ヘッダーと明細は1トランザクションで作る | `create_order_with_requests()`（057/060/073/079/087） |
| R-O-02 | 明細の選択は**予定数量が登録されている商品の一覧から選ぶ**方式を主とし、その他商品は検索併設 | `/requests/new` |
| R-O-03 | 現場名は入力させない。ログインアカウントの担当現場から自動決定する | `current_site_id()`, `user_can_access_site()` |
| R-O-04 | **納期（日付＋時刻）は必須**。現場がオーダー時に入力 | `orders.delivery_deadline`（071） |
| R-O-05 | **ヤード積込日は現場がオーダー時に必須入力**。事務・センターは必要時のみ訂正できる | `orders.yard_loading_date`（073, D-20260806-08） |
| R-O-06 | 依頼は**0.5束単位**まで可。1束20本なら10本単位で依頼できる | `order_unit = lot_size / 2`（065） |
| R-O-07 | 事務は明細の**確定数量を修正**できる。当初数量は `original_quantity` に保持し、帳票で対比できる | `update_stock_request_quantity()`（056） |
| R-O-08 | 事務は紙に手書き追加された明細を**後からオーダーへ追加**できる。同一操作の再送は新しい行を作らない（冪等） | `add_order_item()` + `operation_id`（062/083/085） |
| R-O-09 | 明細の**自社／リース区分**は在庫状況から自動判定し、事務が明細ごとに手で上書きできる | `ownership_auto` / `ownership_override`（064） |
| R-O-10 | 資材発注書を印刷できる。運転手・リフトマン・運送情報・備考は**入力欄を持たず枠だけ**印刷する（手書き運用） | `/orders/[id]/print`（D-20260805-02） |
| R-O-11 | 帳票の「資材種別」はオーダーに含まれる商品分類から**システムが自動判定**する。複数種別が混ざる場合は全て並べる | `materialCategories`（D-20260801-10） |
| R-O-12 | 帳票に**予定数量超過**と**半端もん**の判定を表示する。見込数量は「既出庫＋全未処理オーダー」で算出する | `get_order_plan_status()`（070）, `stock_request_lot_size_status` |
| R-O-13 | 帳票の合計重量を表示する。重量未登録の商品は合計に含めない | `totalWeightKg` |
| R-O-14 | **帳票の内容は発注時点でスナップショット保存**する（発注者名・元請名・元請伝票番号・伝票用現場番号）。後からマスタが変わっても過去の帳票は再現できる | `*_snapshot` 列（066/087） |
| R-O-15 | センターはオーダー詳細から**「出庫完了」で全未出庫明細を一括反映**できる。個別の受付・出庫操作は持たない | `ship_order_to_site()`（072, D-20260806-07） |
| R-O-16 | ヤード名はサンプル市A固定で印字する | D-20260805-02 |

**R-O-17（ステータス）**: 明細のステータスは `requested → accepted → shipped / cancelled`。**在庫減算は `shipped` の時のみ**行い、`requested` / `accepted` では引当も減算もしない（二重引当の回避）。
**R-O-18（在庫不足）**: 在庫が足りなくてもオーダー作成をブロックしない。電話等の現行運用を継続する。出庫確定時のみ `insufficient_stock` で拒否し、`accepted` のまま戻す。
**R-O-19（キャンセル）**: 現場は**自分の `requested` のみ**キャンセル可。事務は `requested` / `accepted` をキャンセル可。`shipped` の取消・再出庫は DB 側で拒否する（`FOR UPDATE` + status guard）。
**R-O-20（承認の廃止）**: 事務による承認は**廃止済み**。承認は出庫判断に使わないため操作経路を閉じた。過去の承認日時のみ監査用に残る（migration 074）。

### 3-3. 在庫管理

| ID | 要件 | 実装 |
|----|------|------|
| R-S-01 | 在庫は「商品 × 保管場所」で持つ。保管場所は `center`（各センター）と現場 | `stock_items`, `storage_kind`, `center_id` |
| R-S-02 | 在庫の増減は**必ず在庫台帳（`stock_ledger`）を伴う**。台帳を経由しない直接更新は行わない | `apply_stock_movement()`（004/018/027/033/089） |
| R-S-03 | 在庫は**マイナスにならない**。不足時は `insufficient_stock` で拒否する | 同上 |
| R-S-04 | 出庫すると現場在庫（貸出在庫）が増える。現場からの返却で減る | `ship_stock_request()`, `return_from_site()` |
| R-S-05 | 現場からの**一括返却**（複数商品をまとめて返却登録）ができる | `return_materials_from_site()`（088） |
| R-S-06 | 返却登録の**訂正**ができる。訂正は台帳へのリンクを保持する | `correct_stock_return()`（080/084） |
| R-S-07 | 事務は在庫を直接補正できる（暫定メンテ経路） | `adjust_stock_item()`（037） |

**R-S-08（過入庫）**: 出庫数を超える返却が申告された場合、**超過分を在庫に加算しない**。
- 通常返却数 = min(返却入力数, 現在の現場在庫)、過入庫数 = 残り
- 通常返却数のみ `stock_items` / `stock_ledger` に反映し、**過入庫は在庫にも台帳にも一切書かない**
- 過入庫は `over_returns` に「未確認／確認済み」で記録する。確認済みにしても在庫数は変えない
- 理由: 旧運用では超過分も在庫に加算していたため、買っていない在庫が増え続け実棚と食い違っていた（migration 046）

**R-S-09（在庫調整申請）**: 現場・センターが在庫の食い違いを申請し、事務が承認／却下する。
- 申請入力は「**実際に数えた数量（絶対値）**」。現場担当者が数え直した結果をそのまま打てる
- 承認時に適用するのは「**申請時のシステム数量との差分（delta）**」。絶対値適用だと申請〜承認間の出庫・返却を打ち消してしまうため
- 同一在庫に未処理の申請は 1 件のみ（部分ユニーク索引）
- **申請者本人による承認・二重承認・承認済みの再処理を禁止**（RPC 内で `FOR UPDATE` + 状態・申請者チェック）

**R-S-10（棚卸）**: センター在庫の棚卸を、**事務とセンターが同じ権限**で実施できる（センター参照専用原則の明示的な例外・D-20260807-01）。
- 状態遷移: `draft`（開始）→ `counted`（実数保存・差異確認）→ `completed`（選択した明細だけ在庫へ反映）
- 実数の保存と在庫反映を分離し、差異を確認してから反映する明細を選べる（086）

**R-S-11（センター間移動）**: サンプル市A→サンプル市Bのようなセンター間移動を記録できる。
- **起票はセンターロールのみ**。自分のセンター（from）から他センター（to）への移動だけ登録できる
- 登録と同時に即時反映（移動元マイナス・移動先プラス）。**事務の承認は不要**（事務は閲覧のみ）
- 移動元の在庫が不足していても**ブロックせず警告のみ**。不足分は `shortage_quantity` に記録して画面に警告表示する
- 記録形式は資材発注書と同じ「ヘッダー＋複数明細」（`center_transfers` / `center_transfer_items`）

### 3-5. 予定数量・警告

| ID | 要件 |
|----|------|
| R-P-01 | 現場×商品ごとに予定数量を登録する（`site_product_plans`）。現場は自現場分を参照できる |
| R-P-02 | 予定数量を超えるオーダーが来ても**ブロックしない**。事務が `/plans/over` と帳票で認知できるようにする |
| R-P-03 | 半端もん（発注可能最小単位の非倍数）も**ブロックしない**。`/plans/lot-size` と帳票で事務が認知できるようにする |
| R-P-04 | 半端もんの判定基準は `lot_size / 2`（0.5束）。`site_products.allow_partial_lot = true`（既定）なら判定しない |

**方針**: 現場の発注は止めない。警告を出して事務が気づける形にする、が一貫した設計原則である（052 のブロック方式は 053 で撤回済み）。

### 3-6. 現場進捗・未返却

| ID | 要件 |
|----|------|
| R-G-01 | 現場の進捗を「組立完了／解体開始／解体完了」の3区分で記録する |
| R-G-02 | 記録時点の**出庫累計・返却累計・未返却数・現場残を確定値として保存**する（後から再現できるようにするため。数値は時間とともに変動する） |
| R-G-03 | 記録は**追記のみ**。訂正は同じ区分を再記録し最新を有効とする（監査証跡を壊さない） |
| R-G-04 | 区分の順序は強制しない（現実には前後しうる）。順序の妥当性は画面の注意表示に留める |
| R-G-05 | 未返却数 = 出庫累計 − 通常返却累計。**過入庫は返却累計に含めない** |
| R-G-06 | 完工レポートを CSV 出力できる |

### 3-7. 仕入れ管理

| ID | 要件 |
|----|------|
| R-B-01 | 仕入れは入出庫登録とは**別機能**として持つ（ヒアリングの明確な意向） |
| R-B-02 | 記録するのは**入荷した時点のみ**。発注→入荷の2段階管理・分納・返品・現場直送はいずれも対象外 |
| R-B-03 | 金額は持たない。購入日・材料・数量・仕入先のみ |
| R-B-04 | 参照・書込とも**事務のみ**。センター・現場には一切見せない |
| R-B-05 | 帳票は不要。一覧参照と CSV 出力があれば足りる |

### 3-8. 分析

| ID | 要件 |
|----|------|
| R-A-01 | ダッシュボード（`/analytics`）、期間別・現場別・商品別・リース会社別の集計を提供する |
| R-A-02 | 各集計を CSV 出力できる |
| R-A-03 | 商品稼働率を在庫台帳を入力として算出する（過入庫は台帳に入らないため混入しない） |
| R-A-04 | 分析は**事務のみ**が参照する |

### 3-9. ユーザー・アカウント管理

| ID | 要件 |
|----|------|
| R-U-01 | 認証は Supabase Auth（メール＋パスワード）。**招待メールによる発行を既定**とする |
| R-U-02 | 現場アカウントは**1現場につき1つ**発行し、業者には紐付けない。表示名は現場名を既定とする |
| R-U-03 | 1アカウントで複数現場を担当できる（`app_user_sites`）。`site_id` は既存データ互換の代表現場 |
| R-U-04 | センターアカウントは `center_id` で地域に紐づく |

| R-U-06 | ユーザーの作成・ロール変更は事務のみ（`configure_app_user_by_admin()`） |

### 3-10. 外部連携（GAS）

既存の Google Apps Script 側の運用に手を入れずに連携する。GAS が Supabase の RPC を**共有シークレット付きで直接呼ぶ**（`anon` に execute 権限を付与し、RPC 内でシークレットを検証する）。

| ID | 要件 |
|----|------|
| R-X-01 | GAS の「稼働現場リスト」を正として、現場マスタを自動作成・更新する（`sync_site_master_from_gas`） |
| R-X-02 | 現場名の重複など取り込めない事象は `gas_site_sync_issues` に記録し、事務が確認できるようにする |
| R-X-03 | GAS の「現場確認」から現場進捗を受け取り、資材スナップショットを自動記録する（`sync_site_progress_from_gas`） |
| R-X-04 | 同じイベントの再送で二重記録しない（`external_event_id` を主キーとする冪等設計） |
| R-X-05 | 連携シークレットは `integration_settings` に保持し、初期値のままでは連携を拒否する |
| R-X-06 | `sites.code`（GAS 連携用 `SITE-xxx`）は変更しない。伝票用の現場番号は別列で持つ |

|----|------|

## 6. 業務フロー（現行）

### 6-1. 資材発注書を軸にした流れ

```
現場（vendor）
  └─ オーダー起票（複数明細・納期・ヤード積込日）
        │
事務（admin）
  ├─ 確定数量の修正 / 明細の追加 / 自社・リース区分の上書き
  └─ 資材発注書を印刷（予定超過・半端もん・合計重量を表示）
        │
センター（center）
  ├─ 発注書を見て資材を積み込む（運転手・運送情報は紙に手書き）
  └─ オーダー詳細で「出庫完了」→ センター在庫が減り、現場在庫が増える
        │
現場で使用 → 解体
        │
事務（admin）
  ├─ 返却登録（一括可）→ 現場在庫が減り、センター在庫が増える
  │     └─ 出庫超過分は在庫に入れず「過入庫」として別記録
  └─ 現場進捗の記録（組立完了 / 解体開始 / 解体完了）＋その時点の確定値を保存
```

### 6-2. 在庫のズレを潰す経路

| ズレの原因 | 対策機能 |
|-----------|---------|
| 出庫超過の返却を在庫に加算していた | 過入庫の分離記録（R-S-08） |
| 実棚とシステム値の食い違い | 棚卸（R-S-10）、在庫調整申請（R-S-09） |
| 現完滅失の登録滞留 | 未返却資材一覧・現場進捗（R-G-01〜06）で可視化 |
| 予定を超える発注・半端な発注 | 超過・半端もんの警告一覧と帳票表示（R-P-02〜04） |
